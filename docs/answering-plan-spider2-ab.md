## 1. 设置

| | 控制组 | 实验组 |
| --- | --- | --- |
| 代码 | `master` `4e23aa2`（方案实施前） | `develop` `6a3ea2e`（Phase 1–5 全部合入，#275–#279） |
| 运行 | `answering-plan-ab-control-001` + `-002`（续跑剩余 15 题） | `answering-plan-ab-treatment-001` |

两组相同：

- **题单**：开发集 35 题（`phase6-development-35-ids.txt`），加冻结集中开发集以外部分每 7 题取 1、共 15 题，合计 50 道 SQLite 题。
- **模型**：`deepseek` 配置（`deepseek-flash`）。
- **运行参数**：`--disable-clarification`，同一份 `config.local.json`，预算、超时、轮数上限相同，同一 Spider2 数据库包。
- **Jev**：两组都已配置但未启用（`resolved: false`，缺少 `TYPESAFE_API_KEY`）。

**执行说明**：两组的部分题目因机器内存不足被中断，均以 `--retry` 开新 attempt 重跑。合并时每题取最后一个以 `completed` 或 `timeout` 结束的 attempt，中断产生的 `infra_error` attempt 不计入。并发只决定几题同时跑，每题仍是独立会话，不影响模型输入。控制组前 34 题以并发 3 运行，其余运行以并发 2 或 1 进行。

**评分口径**：采用 Spider2-lite 官方 `exec_result`，即用发布的 CSV 对比 Gold。官方的 SQL 重执行模式在本机不可用：本地 Spider2 检出中，`evaluate.py` 打开的 `resource/databases/<db>.sqlite` 是 0 字节占位文件，真实库位于 `spider2-localdb/` 子目录，因此两组的 SQL 模式都是 0 分。这一问题对两组完全相同，与被测代码无关。

### 2.1 Spec 调用错误率

方案要求“spec 调用错误率不上升”：

- **按被拒字段计**：从每次调用 0.60 降到 0.51。
- **按工具错误计**：全部工具错误从 22 降到 14；Spec 调用自身的工具错误为 1 和 2，都是个位数。
- **按“含被拒字段的调用”计**：上升 5.3 个百分点。

按原因拆分被拒字段：

| 原因 | 控制组 | 实验组 |
| --- | --- | --- |
| 改写已设字段未附 reason | 24 | 28 |
| 统计总体 / 证据规则 | 27 | 13 |
| 决定前需先跑探针 | 15 | 15 |
| 值格式 | 9 | 13 |
| 结构化字段拒绝旧写法（T5.4） | 0 | 0 |
| 其他 | 28 | 17 |

T5.4 新增的结构化写法在 50 题中没有触发一次拒绝（`measure.countGrain` 被拒 3→4 次、`population.eligibility` 4→3 次，均为其他原因）。“含被拒字段的调用”的增量主要来自“改写已设字段未附 reason”，方案没有改动这一规则，属于运行间波动。结论：按被拒字段和工具错误计，spec 调用错误率没有上升。

“实现错”子集在本题单中只有 2 题，两组都答对，本次没有可观测的修复或回退。

## 3. 结论

- **总正确率提升**：实验组 36/50，高于控制组 31/50，且没有回退题，满足“较基线持平或提升”。
- **spec 调用错误率没有上升**：按被拒字段（0.60→0.51 / 调用）和工具错误（22→14）计。
- **历史错题子集有明确修复记录**：“假定错”子集中 local073 得到修复。

**局限**：

- 50 题、单次运行，差异的置信区间较宽。
- SQL 重执行评分不可用，结果只基于 CSV 评分。
- 两组都没有启用 Jev，因此 Phase 4 T4.1 的差异见证行对 Jev 决策的影响不在本次评测范围内，该项仍待 `TYPESAFE_API_KEY` 与逐字段标注集。
